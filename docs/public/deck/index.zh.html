背景

什么是 Pulsar？

Software Mansion 出品的跨平台、设计师级触觉 SDK。 iOS 原生 Swift、Android 原生 Kotlin，已在 App Store 与 Google Play 上架。

151 个手工调校的 预设，一个 PatternComposer 用来编排任意的离散 + 连续 pattern， 再加一个 RealtimeComposer 处理手势驱动的反馈。 目前都通过一个 React Native TurboModule 暴露给上层。

iOS Swift SDK Android Kotlin SDK React Native (TurboModule) 151 个触觉预设 Apache 2.0

预设可视化

一个触觉 预设，就是带包络的命名 pattern。

Pulsar 的 151 个预设里，每一个都是一段 JSON：包含 离散脉冲（橙色）和 一条 振幅 + 频率的连续包络（绿色）。无论渲染器是 CoreHaptics、VibrationEffect， 还是现在的 Lynx，送到底层 SDK 的 JSON 始终是同一个形状。

强烈刚性Pattern长时

Alarm

急促、不让人忽视。适合关键错误或需要立即响应的紧急场景。

1,130 ms · 6 个离散脉冲 + 13 点连续包络
厚重柔性脉冲长时

FadeOut

优雅地走向静默。适合 dismiss、过渡这类应当平稳自然的交互。

506 ms · 6 个衰减脉冲

Lynx App 端调用 Presets.alarm()，桥的另一端， 原封不动的 Swift / Kotlin SDK 会把完全相同的包络喂给设备的触觉马达。

改动的形状

同一个 hook，两个世界。

usePatternComposer 是 Pulsar App 用来解析、播放 pattern 的 hook； 在 React Native 写一遍，在 Lynx 又写一遍。结构完全一致，差异都是机械性的。

React Native react-native-pulsar/src/usePatternComposer.ts

import { useCallback, useEffect } from 'react';
import Pulsar from './NativeRNPulsar';
import type { Pattern } from './types';
import { useSharableState } from './useSharableState';

// RN prototype-cache workaround
Pulsar.PatternComposer_play;

export default function usePatternComposer(
  pattern?: Pattern,
) {
  const patternId = useSharableState(-1);

  const play = useCallback(() => {
    'worklet';
    const id = patternId.get();
    if (id !== -1) {
      Pulsar.PatternComposer_play(id);
    }
  }, []);
  // ... stop, parse: same shape
}

Lynx lynx-pulsar/src/usePatternComposer.ts

import { useCallback, useRef } from '@lynx-js/react';
import Pulsar from './NativePulsar';
import type { Pattern } from './types';


// no prototype workaround needed


export default function usePatternComposer(
  pattern?: Pattern,
) {
  const patternIdRef = useRef<number>(-1);

  const play = useCallback(() => {


    const id = patternIdRef.current;
    if (id !== -1) {
      Pulsar.patternPlay(id);
    }
  }, []);
  // ... stop, parse: same shape
}

净效果：import 路径、worklet 指令、方法名前缀全部消失。共享可变状态原语降级成一个普通的 useRef。Lynx 的双线程模型本就把 hook 跑在后台线程，不需要任何跨内存桥接。

ReactLynx · 不那么机械的部分

Lynx 真正 不同的地方。

适配层的移植是机械活儿，UI 的移植不是。 ReactLynx 长得像 React，但运行时契约不一样。最先翻车的，往往是 React 写法里你第一反应就会用的那些东西。

不能用条件 JSX
{cond && <X/>} 和三目都会 把双线程 snapshot 系统打崩。 正确写法是两个分支都渲染，用 style={{ display: ... }} 切换。这个 App 里每个 tab 面板、每个 demo 子页都常驻在树上。
display: none 不够
flex 容器里的 display: none 并不能稳定隐藏子节点。 可靠的做法是 position: absolute + width/height: 100% + zIndex， 父节点配 overflow: hidden。
不能在 .map() 里用动态 key
用 key 强制重挂、或者在 .map() 里切 display:none， 都会触发 snapshotPatchApply / insertBefore 崩溃。列表内部用 opacity 加绝对定位代替。
元素与事件
<View> → <view>，<Text> → <text>， onPress → bindtap，onTouchStart → bindtouchstart。 文字必须放进 <text>；view 里裸的字符串会编译报错。
CSS 现实
text-transform 不支持。长度必须带单位（"24px"，不是 24）。 display: flex 默认方向是 row。overflow: scroll 不支持； 用 <scroll-view scroll-y>。<image> 必须给明确的像素尺寸。
没有 gesture-handler
Playground 里的滑动绘制和 Slider demo，都是用裸 bindtouchstart/move/end 重写的。 Sensor Haptics demo 那个加速度计驱动的小球，因为没有可用的传感器 API，最后退回成触控拖拽，物理参数保持不变。
NativeModules 的双线程保护
NativeModules 只在 后台线程 存在；主线程负责求值 JSX snapshot。适配层用 typeof NativeModules !== 'undefined' 包一下，让模块文件在两条线程上都能安全 import。

可复用

Slopfork 配方。

下一次移植 (Reanimated、Skia、Gesture Handler， 或任何长着 Native Module 形状的库) 沿用这套顺序就好。

  1. 先 adapter，后 UI。用 test-sync-returns/ 这种 harness 把 TS 表面锁住，再去碰任何 view 代码。
  2. 先做最小 demo，再做完整版。一个一次性的测试 App 把每一条 API 调用都跑一遍；完整移植在 ReactLynx 翻车时，可以退回最小 demo 排查。
  3. 把约束写进 AGENTS.md。"不要条件 JSX"、"单文件"、"用 scroll-view 不要用 overflow"，全部白纸黑字写下，从 CLAUDE.md 路由进来，每篇 PRD 都链回去。
  4. 每一个工作单元一篇 PRD，附 Verification Protocol。lynx-docs 查询 → npm run build → DevTool 截图 → console error 检查。每一个 story 都走一遍。
  5. 编译通过不等于完工。必须端到端在真机上验证，才能宣称一个 story 是绿的。

"编译通过 ≠ 能用。必须端到端验证。"
